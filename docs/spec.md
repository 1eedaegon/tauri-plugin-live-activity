# Feature specification

What tauri-plugin-live-activity promises, one requirement per row. Each ID is named by the tests that prove it, and
`tools/spec-coverage.sh` fails when a requirement has no test, a listed test does not exist or does not name it right
above its declaration, or a test names an ID this file lacks.

Levels: **unit** (Rust, `cargo test` on the host), **node** (`npm test`), **kotlin** (the Gradle tests of the Android
library: unit tests on the JVM, and `NativeBridgeTest` on an emulator or a phone), **simulator** (`tests/ios/run.sh`: the
demo app on an iOS Simulator).
Errors are the codes of the plugin's `Error { code, message }`, which JavaScript receives as `{ code, message }`.

The plugin is an adapter of the [`liveactivity`](https://github.com/1eedaegon/liveactivity-rs) crate: the contract, its
checks, the lifecycle and the backends of both platforms are that crate's, and the plugin adds Tauri's commands, events,
configuration, the Android permissions and the JavaScript API. On iOS liveactivity calls the
[`activitykit`](https://github.com/1eedaegon/activitykit-rs) crate, whose Swift layer talks to ActivityKit, and the app's
widget extension links activitykit's Swift products; the plugin has no Swift of its own. On Android liveactivity runs
every activity on the liveupdate crate and projects the layouts; the plugin's Android library carries liveupdate's
adapter. Desktop has no backend. What liveactivity proves by its own tests is listed under
[Proven by the liveactivity crate](#proven-by-the-liveactivity-crate).

## The JSX entry

`tauri-plugin-live-activity/jsx` writes layouts as TSX. It is a JSX import source of its own (`jsxImportSource`), so a
`.tsx` file needs no React; its components return the same plain node objects as the `layout` builders.

## Pushes

| ID | Requirement | Example | Error | Platform |
| --- | --- | --- | --- | --- |
| TP-PUSH-1 | A layout start may carry `push`: `"token"` asks ActivityKit for a push token of the activity's own, `{ "channel": "<id>" }` subscribes it to a broadcast channel (iOS 18; `UNSUPPORTED_FEATURE` with `pushChannel` and `18.0` below). | TP-PUSH-4 | Content a push delivers reaches JavaScript as `live-activity://updated` with the activity's record, through `onUpdated`: activitykit's `Event::Updated`, content above every revision the process sent or accepted, so the app's own updates do not come this way. | TP-PUSH-5 | `checkPermissions` reports `frequentPushes`: `granted` or `denied` from activitykit's `frequent_pushes` (Settings, with `NSSupportsLiveActivitiesFrequentUpdates`), `notApplicable` where there are no pushes. `getCapabilities` reports `push`: `supported` on iOS where Live Activities are, `unsupported` on Android and desktop. | TP-PUSH-6 | The events of pushes, and those of an activity's life (TP-EVENT-1), go to JavaScript as the liveactivity crate reports them, one at a time on one thread (liveactivity's events thread on iOS, the plugin's draining thread on Android), without waiting for JavaScript. A tap is reported on the same thread and holds it until the handlers of `on_action` have run and its event went out, at most 4 s (TP-ACTION-3): an event behind a tap comes after that tap's handlers, where 0.6 sent it at once. Tauri runs the app's Rust listeners of these events inline on that thread: one that blocks delays the taps and the events behind it, and one that panics is caught in the plugin's sink, so that the thread, the taps and the events to JavaScript go on. A Rust listener of `live-activity://action` that panics does not end the taps either. | TP-PUSH-7 | The React hook listens for push events only when the options carry `push`, which is read at start; a subscription the plugin refuses lands in the state's `error`. The state carries `pushToken`, the running activity's latest token (one that came before the start answered, or one the plugin held, included) or `undefined`, and takes the record of an `updated` event of its activity as its `record`; the component's values stand as last sent, so pushed content stays until they change. The next change goes above every revision seen: the pushed one, the one a start answered with (a repeated keyed start is at the running activity's revision) and the one an update in flight was answered at. Events of other activities change nothing. | — | — | all |
| TP-PUSH-8 | `pushTokens()`, the command `push_tokens` and `push_tokens()` in Rust answer the tokens the plugin holds since launch: the newest token of each of the last 32 activities that got one, in the order their first tokens came, and the app's push-to-start token, each noted before its event goes out. ## Proven by the liveactivity crate

The plugin keeps these promises without code of its own. The behavior and the tests that prove it are the
[`liveactivity`](https://github.com/1eedaegon/liveactivity-rs) crate's, on which every command of the plugin runs;
the plugin's own tests prove that its commands, its Rust API and its events carry that crate's contract unchanged
(TP-RUST-2, TP-RUST-3, TP-JS-7, TP-CONTRACT-8). The requirements keep their ids for reference, and
`tools/spec-coverage.sh` does not count them.

- TP-RUST-4 (all): An error of activitykit keeps its code; its message is activitykit's text, with the feature and iOS version of `UNSUPPORTED_FEATURE` and the scope of `SYSTEM_LIMIT`. Errors: every code.
- TP-CONTRACT-7 (all): The value key `liveActivityTemplate` is the plugin's: on iOS it marks the activities of contract v1's templates. A contract v2 start, update or end whose values hold it fails on every platform, in the commands and in the Rust API, before any backend sees it. activitykit's contract does not know the rule. Errors: `INVALID_INPUT`.
- TP-IOS-4 (iOS): An update or end of an id that activitykit does not know fails, and so does an update of an ended activity. Errors: `NOT_FOUND`.
- TP-IOS-7 (iOS 17.2+ (ActivityKit)): A snapshot's `timestamp` goes to activitykit as the content's time, at a start, an update and an end; without one activitykit takes the time of sending. A record carries the timestamp of the accepted content. Errors: `INVALID_INPUT` above the largest time.
- TP-IOS-8 (iOS 16.2+): A record's state is activitykit's: `pending`, `active`, `stale`, `ended`, `dismissed` or `unknown`.
- TP-IOS-9 (iOS): `get_capabilities` reports activitykit's authorization: with Live Activities supported every feature but `actions` is `supported` and `actions` follows `buttons` (iOS 17); without them every feature is `unsupported` and the backend `unsupported`. `maxPayloadBytes` is 4096.
- TP-IOS-10 (iOS): `check_permissions` reports `liveActivities` as `granted` when enabled and `denied` otherwise, `notApplicable` when unsupported; `request_permissions("liveActivities")` reports `settingsRequired` instead of `denied`; another kind fails. `notifications` and `promotion` are `notApplicable`. Errors: `UNSUPPORTED_FEATURE`.
- TP-IOS-12 (iOS): activitykit's errors reach JavaScript with their codes, `NOT_FOREGROUND` for a start that ActivityKit refuses outside the foreground among them. Errors: `UNSUPPORTED_PLATFORM`, `PERMISSION_DENIED`, `NOT_FOREGROUND`, `CONFIGURATION_REQUIRED`, `SYSTEM_LIMIT`, `UNSUPPORTED_FEATURE`, `NATIVE_ERROR`.
- TP-IOS-13 (iOS): With `receipts: "redacted"` in the plugin configuration the plugin builds activitykit's kit with redacted receipts, which keep a digest instead of the values: starts, updates and ends work, and after a relaunch a list gives the values that ActivityKit shows. A kit that already runs in the process with other settings makes the plugin's setup fail with the kit's error. The kit's settings come from the configuration alone. Errors: setup error (`CONFLICT`).
- TP-IOS-14 (iOS): `write_image` checks the PNG, then activitykit writes it to `activitykit/images` in the App Group that the widget extension names under `ActivityKitAppGroup`. Errors: `INVALID_INPUT`, `PAYLOAD_TOO_LARGE`, `CONFIGURATION_REQUIRED`, `NATIVE_ERROR`.
- TP-IOS-15 (iOS): Live Activities need iOS 16.2 on an iPhone, iPadOS 17 on an iPad; below that every command but the reads fails. Errors: `UNSUPPORTED_PLATFORM`.
- TP-IOS-16 (iOS): The plugin's requests become activitykit's field by field: a start its layout, values, key and revision, and its stale date and timestamp when given; an update its values and revision, and its stale date and timestamp when given; an end its policy (`immediate`, `default`, `after` a time) and, when given, its final values, revision, stale date and timestamp. Times are epoch milliseconds; a time after 9999-12-31T23:59:59.999Z, a cap every platform's `SystemTime` holds, is that time (a later one overflows on Windows), so an iOS record reports the capped time where Android echoes the request.
- TP-IOS-17 (iOS): Ending again reaches an activity that ended at once and that the system no longer lists through a handle the plugin keeps: one for each of the last 64 activities that ended in this launch, in the order of their first end, however often each is ended. An older one, and any one after a relaunch, is `NOT_FOUND`. Errors: `NOT_FOUND`.
- TP-V1-3 (iOS): The two contract versions do not see each other's activities: `list` gives template activities only and `list_layout` layout activities only, and an id of one version is not found by the other's commands. Both start through activitykit's keys, so a template and a layout activity cannot run under one activity key. Errors: `NOT_FOUND`, `CONFLICT`.
- TP-V1-4 (all): The largest template snapshot (120 and 240 code points of four bytes each) fits the contract's weight with its layout.
- TP-ANDROID-1 (Android): A layout snapshot takes a `timestamp`, which the record carries back. Errors: `INVALID_INPUT` out of range.
- TP-ANDROID-2 (Android): `end_layout` with final content checks it against the start as an update, and the activity ends with it: the returned and the stored record carry it. Android cancels the notification at the end (`immediate`, `default`; `after` stays `UNSUPPORTED_FEATURE`), and a dismissed activity keeps its last snapshot. Errors: `STALE_REVISION`, `CONFLICT`, `INVALID_INPUT`.
- TP-ANDROID-3 (Android): Android layouts run on the liveupdate crate as schema-v2 requests: liveactivity projects the request and keeps the layout request and its latest snapshot in a store of its own, at the path the plugin names (`tauri-live-activity/layouts.json`), and liveupdate keeps the lifecycle, the receipts and the notification. Records read back into the plugin's types with the layout snapshot from the store; a liveupdate record the store does not know is left out, and its id is `NOT_FOUND`. Errors: `NOT_FOUND`.
- TP-ANDROID-4 (Android): On Android the progress and timer templates of contract v1 run on the liveupdate crate too: a start becomes liveupdate's private start request; the conversion boundary adds backend `androidNotification` to the Android-only core record; capabilities follow its promotion; its errors keep their codes, an unknown one becoming `NATIVE_ERROR`; `list` shows only schema-v1 records and `listLayout` only schema-v2 ones. Errors: liveupdate's codes, `NATIVE_ERROR`.
- TP-ANDROID-5 (Android): The liveupdate template of a layout comes from its lock screen tree, conditions aside, and stays for the generation: the first `progress` node gives Progress (one segment of 1000, the value clamped to 0..1), else the first `timerText` gives Timer (counting down unless `countsDown` is false), else two or more `text` nodes give BigText, else Standard. The first shown progress gives the value, 0 when none shows; the first shown timer gives the times, else the first timer of the tree with its keys' current values, an end not after the start being one millisecond after it.
- TP-ANDROID-6 (Android): Shown `text` nodes, in document order through every stack: the first is the title (the app's name when there is none or it is blank), the second the status and the BigText text; a missing status is the chip text, then the title. Bound values print as JavaScript's `String` prints them, blank means liveupdate's whitespace (`U+FEFF` included), and texts are cut to liveupdate's limits (title 120, status 240 code points) with `…`.
- TP-ANDROID-7 (Android): Shown buttons with a shown text become notification actions, at most 3, one per action id: the action id, the first shown text inside as the title (cut to 64), no icon, no authentication. The first shown image with a `file` that exists in the image folder, at most 1024 px a side and 1 MiB, is the large icon. The chip text is the progress percentage (`65%`) when a progress shows and no timer. With `android.samsungNowBar` the Now Bar gets the title and the status.
- TP-ANDROID-8 (Android): `degradedFeatures` lists liveupdate's (`nativeLiveActivity` first), then `layout.<type>` once per type for every shown node the projection leaves out, in document order, then `layout.island`, `layout.styles`, `layout.background` and `layout.keyline` for the parts the request has.
- TP-ANDROID-9 (Android): The v2 lifecycle on Android: the same keyed start returns the running activity, another start under its key is `CONFLICT` even when it projects the same; an update needs a higher revision (`STALE_REVISION`), the same revision with other values is `CONFLICT` and with the same values returns the record, and an ended or dismissed id is `NOT_FOUND` before any of that; the same start again keeps the latest values; a start that liveupdate refused, or whose answer was lost, leaves a pending entry that the next command adopts when the activity runs and drops otherwise; an end with final content updates and then ends; `after` is `UNSUPPORTED_FEATURE`; records keep the layout snapshot, and the store forgets activities that liveupdate no longer keeps. Errors: `CONFLICT`, `STALE_REVISION`, `NOT_FOUND`, `UNSUPPORTED_FEATURE`.

## Not proven by a test

- TP-PUSH-1 to TP-PUSH-4, TP-PUSH-8: No test receives a token or a push: the simulator has no APNs and the demo app no Push Notifications capability, and a device test needs the app's APNs key and a server. The plugin's unit tests hand its sink the events as liveactivity reports them, liveactivity's feed its fake kit, and the simulator suite's lifecycle checks start with `push: 'token'` only to see ActivityKit refuse it (`CONFIGURATION_REQUIRED`) and the plugin hold no token. That a token of a relaunched activity or the push-to-start token reaches a page through a real webview rests on the replay of TP-PUSH-8, proven with the mock IPC. `UNSUPPORTED_FEATURE` for a channel below iOS 18 is activitykit's rule; the plugin has no test of it. That a repeated keyed start asking for another push is the running activity is proven against liveactivity's fake kit; the real rule is activitykit's fingerprint, which leaves the push out. `frequentPushes` is `denied` as well when the app offers no switch (no `NSSupportsLiveActivitiesFrequentUpdates`): activitykit reports one value for both.
- TP-IOS-2, TP-IOS-13: a repeated start after a relaunch, and redacted receipts, are activitykit's; its own tests
  drive them on a simulator, and liveactivity's unit tests check what is sent and built.
- TP-IOS-5, TP-IOS-17: a repeated end reaches activitykit's record of the ended activity through a handle that
  liveactivity keeps. After a relaunch, an activity that ended at once and that the system no longer lists is `NOT_FOUND`,
  because activitykit finds an id only through a live handle or the system's list; liveactivity's fake kit models that
  list.
- TP-IOS-7: ActivityKit uses a content's timestamp from iOS 17.2; the simulator runs iOS 26, where only the request
  that activitykit receives is checked (by the unit tests).
- TP-IOS-12, TP-IOS-15: `NOT_FOREGROUND`, `SYSTEM_LIMIT` and an old iOS come from ActivityKit; the unit tests map each
  activitykit error, and activitykit's own simulator tests drive `NOT_FOREGROUND`.
- TP-ACTION-1, TP-ACTION-3, TP-IOS-13: what takes activitykit's `Event::Action` apart and acknowledges it runs on
  iOS only and is liveactivity's (`ios::kit`); the plugin's `src/ios.rs` builds the kit from the configuration and
  runs on iOS only too. activitykit makes neither an event, an activity nor an acknowledgement outside its crate,
  and builds no kit with other settings off iOS, so no host test can run them; liveactivity's unit tests run the
  logic around them on a fake kit, and the plugin's test the dispatcher that holds a tap for the handlers. On the
  simulator, test2, test6 and test7 tap buttons through them.
- TP-ACTION-3, TP-E2E-5: when the tap's intent returns is activitykit's, and the simulator does not show it. The unit
  tests prove that the dispatcher releases a tap only after a 1 s handler and the event and that the plugin's sink
  returns only then, and liveactivity's that the intent is held until the sink returns; on the simulator a tap that
  launches the app in the background shows the update of a 1 s handler.
- TP-E2E-6: `tests/ios/run.sh` runs `tauri ios dev` with connected iPhones hidden from it, and answers Tauri's
  archive step with the simulator build, which on an Intel Mac would otherwise need a signing team (Tauri CLI 2.12.4).
  The debug build, its install and launch, and the server of the page are Tauri's. `tauri ios dev` runs with its
  watcher: with `--no-watch` it ends once it has launched the app, and the server of the page ends with it.
- TP-ANDROID-10, TP-ANDROID-13: `NativeBridgeTest` is an instrumentation test: it runs on an emulator or a phone
  (`connectedDebugAndroidTest`), which CI does not start; CI builds it, and it sees the permissions only with
  notifications allowed. Android's dialog and Tauri's memory of a cancelled one are theirs: the unit tests prove the
  plugin's policy over their answers, on the JVM. No counted test shows the dialog or stores the refusal it observed;
  `tests/android/permission-dialog.mjs` drives the dialog of an installed demo by hand.
- TP-PUSH-6: that Tauri still sends an event to the web views after a Rust listener panicked is read from Tauri's
  source, which sends to them first; the mock runtime of the unit tests has no web view to see it.
- TP-ANDROID-10, TP-ANDROID-12: the plugin's Android transport in Rust (`src/android.rs`: the bridge to the Kotlin
  side, the thread that drains liveupdate's events and the channel that wakes it) is compiled for Android alone. No
  host test runs it; CI checks it with clippy for the Android target, and the demo on a device drives it. The test of
  TP-ANDROID-10 ends at liveupdate's reply to `events`: that the tap then reaches the handlers with its key is
  liveactivity's, with its own tests.
